\section*{Abstract}

The National Flood Insurance Program (NFIP) Redacted Claims dataset is
the primary public record of flood losses in the United States, but
two limitations of the raw data constrain its use for location- and
date-sensitive analysis. First, locations are deliberately obscured to
protect policyholder privacy. Each claim carries only a census block
group, a ZIP code, and a latitude/longitude rounded to one decimal
degree, rather than an exact address. Second, for some claims tagged as
rain-driven (pluvial) flooding, the reported loss date does not
coincide with any local rainfall event, likely reflecting reporting
delays or processing errors. Here we present a cleaning pipeline and
derived dataset that (1) converts all dollar amounts to a constant
reference year, (2) combines the three location signals into a single
bounded polygon per claim using a boundary-matching approach validated
against the data itself, and (3) corrects likely erroneous dates for
pluvial claims by checking each claim's local rainfall record against
NOAA's Analysis of Record for Calibration (AORC) precipitation data.
The pipeline is fully scripted and reproducible from public sources,
with all refinement choices exposed as configurable parameters.

\section*{Background \& Summary}

The NFIP, administered by the Federal Emergency Management Agency
(FEMA), is the principal source of insured flood-loss data in the
United States and is widely used in flood-risk, climate, and
disaster-economics research~\cite{nelson-mercer_pluvial_2025, wing_new_2020,shin_systematic_2022, petkov_learning_2025,garcia_reconstructing_2025,yang_predicting_2022,salas_learning_2023}.
%
FEMA publishes a redacted extract of individual claims (OpenFEMA's \emph{FIMA NFIP Redacted Claims v2})~\cite{fema_nfip_claims_v2}, which is publicly available, freely accessible, and regularly updated.
%
However, redaction leaves several properties of the raw records unsuitable for location or date-sensitive analysis without additional processing.

Location information is redacted for privacy. No street address is provided.
%
Instead, each record is accompanied by the claim's census block group FIPS code, its reported ZIP code, and a latitude/longitude pair rounded to one decimal degree.
%
These constitute three coarse approximations to the claim's true location, none of which alone constrains it tightly.
%
Past work using redacted NFIP claims has often relied on this rounded latitude and longitude alone as a proxy for claim location.
%
However, analyses that would benefit from more precise location information require higher spatial resolution than this proxy affords, particularly for the understudied case of pluvial flooding.

Reported loss dates are also imperfect for a subset of claims~\cite{shin_systematic_2022}.
%
NFIP identifies pluvial (rain-driven) flooding claims via \texttt{causeOfDamage == "4"}.
%
However, for these claims, the reported \texttt{dateOfLoss} does not always coincide with a day of actual rainfall at the claim's location.
%
For instance, in our subset of NFIP claims, to be described below, around 7.5\% of pluvial claims have a maximum hourly accumulated precipitation of 0.0mm over the reported date of loss with reference to the NOAA Analysis of Record for Calibration (AORC) archive ~\cite{fall_analysis_2023}.
%
This pattern is more consistent with reporting delays, adjuster lag, or transcription error than with the true date of the flood-inducing event.

To advance the modeling of pluvial flood incidence, risk, and associated damages, this paper describes an open, reproducible pipeline that addresses both problems using only public data, namely FEMA's own claims extract, the Federal
Reserve Economic Data (FRED) personal consumption expenditures price
index, U.S. Census Bureau cartographic boundary files, and NOAA's AORC
v1.1 archive~\cite{fall_analysis_2023}. 

The resultant dataset is thus a spatially and temporally refined dataset of pluvial NFIP claims, where we associate each reported pluvial claim with a polygon that bounds the claim's true location and, for claims with a loss date on or after AORC coverage begins (1979-02-01) and evaluable precipitation data, a corrected date of loss.
%
We further design the dataset construction script so that it exposes pertinent refinement parameters that can be tuned to different assumptions and needs of the downstream tasks.
%
Both the dataset and the pipeline code that produced it are released under an open license.

\section*{Methods}

The pipeline processes FEMA's public claims extract in three ordered
stages, namely inflation adjustment, spatial triangulation, and pluvial
date correction. Each stage is implemented as an independent,
re-runnable script. The full sequence is defined in
\texttt{src/run\_pipeline.sh} in the code repository (see Code
Availability).

\subsection*{Input data}

\begin{itemize}
  \item \textbf{FEMA OpenFEMA} --- FIMA NFIP Redacted Claims v2~\cite{fema_nfip_claims_v2}, snapshot retrieved 2026-08-13. This is provided in the public domain by the Federal Emergency Management Agency (FEMA) with no authentication required. Because OpenFEMA updates this extract on an ongoing basis, later retrievals will not reproduce this exact claim count.
  \item \textbf{FRED} (Federal Reserve Bank of St. Louis) --- Personal
    consumption expenditures price index, series
    \texttt{DPCERD3Q086SBEA}~\cite{fred_dpcerd3q086sbea}. This is provided in the public domain as a CSV file with no authentication required.
  \item \textbf{U.S. Census Bureau} --- Cartographic boundary shapefiles, block groups and ZIP Code Tabulation Areas (ZCTAs). This is made available per decadal census. Its matching strategy with the NFIP claims is configurable as flags, with the default behavior below. This is provided in the public domain with no authentication required.
  \item \textbf{NOAA} --- Analysis of Record for Calibration (AORC) v1.1~\cite{fall_analysis_2023}, 30 arc-second ($\sim$800 m) grid, hourly. This is made available via Amazon Web Services (AWS) at \texttt{s3://noaa-nws-aorc-v1-1-1km}. No authentication is required.
\end{itemize}

% None of these sources is redistributed in raw form in the code
% repository. Each pipeline step downloads, or expects a locally staged
% copy of, its input, documented at the point of use.

the District of Columbia (CONUS). NFIP claims also exist for Alaska,

design, not as an incidental side effect of processing, because both
the Census cartographic boundary conventions and AORC's grid extent
treat CONUS as a distinct product from these territories. The released
file is further restricted to claims coded \texttt{causeOfDamage ==
"4"}, matching the pluvial focus.

\subsection*{Stage 1 --- Inflation adjustment}

Every dollar-denominated claim field (paid amounts, coverage limits,
building/contents value, replacement cost) is rescaled to a fixed target
year's dollars using the FRED PCE price index, matched to each claim's
loss quarter. The default target year is 2021 and is configurable.

\subsection*{Stage 2 --- Spatial triangulation \emph{(Spatial refinement)}}

Each claim carries three independent, imprecise location signals,
namely a census block group FIPS code, a ZIP code, and a rounded
latitude/longitude. Triangulation intersects whichever of these signals
are available into a single polygon per claim, yielding a strict upper
bound on the claim's true location that is typically substantially
smaller than the region implied by any single source alone.

\textbf{Boundary assignment.} Here and throughout the rest of this
paper, a \emph{release} means a specific dated edition of a Census boundary
shapefile, for example the 2010 or 2020 block-group shapefile, and is
unrelated to the release of this dataset itself. Census block-group
and ZCTA boundaries are redrawn each decennial cycle, so multiple
releases exist for a given geography.
%
Rather than matching each claim to the boundary release nominally in effect at its loss year,
boundary-release assignment is a run-time choice, selected
independently for block group and ZCTA via a strategy parameter with
four options.

\begin{itemize}
  \item \texttt{default} --- for block group, the 2010 release before a
    configurable cutover year and the 2020 release from that year on.
    For ZCTA, equivalent to \texttt{closest} below, selecting whichever
    configured ZCTA release's year is numerically nearest the loss
    year, including loss years before 2000.
  \item \texttt{closest} --- whichever configured release's year is
    numerically nearest the claim's loss year, ties broken toward the
    newer release.
  \item \texttt{most\_recent} --- always the newest configured release,
    regardless of loss year.
  \item \texttt{drop} --- do not use that source.
\end{itemize}

The released dataset uses \texttt{default} for both
block group and ZCTA.
%
Official block group shapefiles do not exist nationwide before 1990, and ZCTA shapefiles exist only from the 2000 census onward.
%
Under \texttt{default}, block group is still attempted against the
2010 release regardless of how far the loss year precedes 1990, and
ZIP is matched to whichever configured ZCTA release is numerically
closest to the loss year, including loss years before 2000, where the
2000 release is the closest available (See \emph{Technical Validation}).

Once a \emph{release} is selected, or unselected in the case of \texttt{drop}, we compute the spatial intersection of the boundaries (i.e. claim polygon = $\bigcap_{i=1}^{n} \text{polygon}_i$, where $n$ is the number of contributing sources).
%
In the worst case, we fall back to the $0.1 \times 0.1$ degree box defined by the rounded latitude/longitude, but in almost all cases the intersection of the three sources is a substantially smaller polygon.
%
Our achieved spatial refinement is, however, not uniform in space and significantly favors urban regions with dense block-group and ZIP coverage over rural regions with sparse coverage.

\subsection*{Stage 3 --- Pluvial date correction \emph{(Temporal refinement)}}

For each claim coded \texttt{causeOfDamage == "4"}, the reported
\texttt{dateOfLoss} is checked against whether it coincides with a day
of meaningful precipitation (maximum hourly precipitation exceeding a
threshold, default 7.62 mm) at the claim's triangulated location.
Peak hourly intensity, rather than daily-accumulated rainfall, is used
as the criterion because pluvial flooding is characteristically caused
by localized, intense rainfall and is conventionally assessed using
local hourly rainfall records~\cite{guerreiro_pluvial_2017}. Pluvial
flooding occurs when rainfall exceeds local drainage capacity within
the short time it takes runoff to reach a drain or low point, so its
risk is governed by short-duration rainfall intensity rather than by
rainfall accumulated over a full day.

To define this threshold, we refer to the NOAA AORC hourly accumulated precipitation product.
%
If the reported date's precipitation does not exceed the defined threshold, a window of nearby days (default $\pm$7) is searched for the day with the daily maximum hourly accumulated precipitation, and if that day clears the threshold it is treated as the corrected date.
%
Within the window, the corrected date is chosen as the day with the
greatest precipitation rather than the day nearest the reported date.
This follows from a monotonic prior between precipitation intensity
and pluvial flood risk. Among the days in the window that clear the qualifying
threshold, the day with the highest precipitation is taken as the most
probable candidate for the claim's true flood-triggering event,
independent of which candidate day is closer in time to the reported
date.
%
The original \texttt{dateOfLoss} is never overwritten. The corrected value and an explicit status code are added as new columns, letting downstream users decide whether to apply
the correction.

The precipitation threshold used to judge whether a day counts as meaningful rainfall is configurable, either as a single constant or as a spatial field.
%
This should reflect the prior beliefs, assumptions, and needs of the downstream tasks.
%
A spatial field may be useful, as there is no principled reason a claim in an arid region and a claim in a persistently wet region should require the same amount of rainfall to qualify as \emph{meaningful}.

\begin{itemize}
  \item \textbf{Constant} --- the default, a single value applied
    everywhere. The script defaults to 7.62 mm (0.30 in), the threshold
    the American Meteorological Society's Glossary of Meteorology uses
    to define \emph{heavy} rainfall intensity~\cite{ams_glossary_rain},
    but this is configurable at run time.
  \item \textbf{Spatial field} --- a user-supplied NetCDF raster
    sampled at each claim's exact location, giving a spatially varying
    threshold without requiring the raster to share AORC's grid or
    resolution.
\end{itemize}

Day boundaries are evaluated in each claim's own local time zone,
resolved geographically per claim location, rather than a single
national reference clock, and daylight-saving transitions are handled.
% 
Precipitation at each claim's triangulated polygon centroid is computed by bilinear interpolation of the four surrounding AORC grid pixels.

AORC coverage for CONUS begins 1979-02-01. Pluvial claims before this
date, and claims for which AORC has no data at the triangulated
location (e.g.\ outside the grid extent, or a small land mass whose
surrounding grid points are all ocean pixels), are not evaluated for
date correction. These claims are retained in the released file rather
than dropped. \texttt{correctedDateOfLoss} falls back to the originally
reported \texttt{dateOfLoss}, and \texttt{pluvialCorrectionStatus} is
set to \texttt{before\_aorc\_coverage} or
\texttt{no\_aorc\_data\_in\_window} accordingly (see Data Records).

\section*{Data Records}

The dataset is released as a single columnar file
(\texttt{claims\_pluvial\_corrected.parquet}, Apache Parquet format) at
claim-level granularity. All original columns from the FEMA OpenFEMA
\texttt{FimaNfipClaims} extract are preserved unchanged (see FEMA's
data dictionary for definitions). The columns added by this pipeline
are as follows.

\textbf{Added by inflation adjustment.}
\begin{itemize}
  \item \texttt{\{field\}Real2021} for each of 15 dollar-denominated
    fields (paid amounts, coverage limits, building/contents value,
    replacement cost), rescaled to 2021 dollars.
  \item \texttt{amountPaid} / \texttt{amountPaidReal2021} --- sum of the
    three \texttt{amountPaidOn*Claim} fields.
  \item \texttt{damageAmount} / \texttt{damageAmountReal2021} ---
    \texttt{buildingDamageAmount + contentsDamageAmount}.
\end{itemize}

\textbf{Added by triangulation.}
\begin{itemize}
  \item \texttt{geometry} (polygon, EPSG:5070 Albers Equal Area) --- the
    intersection of whichever of \{block-group boundary, ZCTA boundary,
    latitude/longitude box\} were available and spatially validated for the claim.
    Claims with zero contributing sources, or whose sources fail to
    overlap one another, are excluded from the released file.
  \item \texttt{n\_geometry\_sources} (1--3) and
    \texttt{geometry\_sources} (e.g. \texttt{"block\_group+zip+latlon"})
    --- record which sources contributed.
  \item \texttt{block\_group\_vintage\_used} and
    \texttt{zip\_vintage\_used} --- the boundary-release year (e.g.\
    1990, 2000, 2010, or 2020) selected for the claim by the
    block-group and ZIP release-matching strategies, respectively (see
    Methods). The two need not agree, even when both strategies are
    left at \texttt{default}.
  \item \texttt{block\_group\_match\_status} --- one of
    \texttt{not\_found}, \texttt{validated},
    \texttt{unvalidated\_no\_latlon}, \texttt{spatially\_inconsistent},
    \texttt{dropped\_by\_strategy}, or \texttt{no\_vintage\_selected}.
  \item \texttt{zip\_match\_status} --- the same status values as
    \texttt{block\_group\_match\_status}, plus
    \texttt{before\_zcta\_coverage} for claims that predate ZCTA
    coverage under the \texttt{default} strategy.
\end{itemize}

\textbf{Added by pluvial date correction.}
\begin{itemize}
  \item \texttt{correctedDateOfLoss} --- the reported date if it
    already coincided with meaningful precipitation, the corrected date
    if a correction was made, or the original date otherwise (always
    populated).
  \item \texttt{pluvialCorrectionStatus} --- one of
    \texttt{before\_aorc\_coverage}, \texttt{accepted\_as\_reported},
    \texttt{corrected}, \texttt{no\_qualifying\_precip\_in\_window}, or
    \texttt{no\_aorc\_data\_in\_window}.
  \item \texttt{reportedDateMaxPrecipMm} --- the maximum hourly
    precipitation (mm) found at the claim's location on the originally
    reported \texttt{dateOfLoss}, before any correction. This is the
    value checked against the threshold to decide whether correction is
    attempted at all.
  \item \texttt{pluvialCorrectionMaxPrecipMm} --- the maximum hourly
    precipitation (mm) found at the claim's location on the date
    \texttt{correctedDateOfLoss} refers to.
\end{itemize}

\texttt{geometry} uses EPSG:5070 (meters). The original FEMA
\texttt{latitude} / \texttt{longitude} fields remain in WGS84
(EPSG:4326) degrees, unchanged.

\section*{Technical Validation}

\subsection*{Boundary-release assignment}

This subsection checks whether the boundary release a claim is matched
against actually corresponds to a plausible location for that claim,
using each claim's own reported coordinates as an independent check on
the string-based GEOID match, rather than assuming a code match alone
means the claim is correctly located. Throughout this subsection, each claim's reported latitude and
longitude, rounded by FEMA to one decimal degree, is treated as ground
truth for the claim's true location, giving a $0.1 \times 0.1$ degree
box the claim must fall within. 

For a given release, \emph{Match} is the raw rate at which a claim's block-group or ZIP code string matches a GEOID
in that release's shapefile. \emph{Valid} is computed only over the matched
claims, and reports the share of those matches whose polygon also
overlaps the claim's ground-truth latitude/longitude box, exactly the
spatial-consistency check described in Methods. A high Match rate with
a low Valid rate would mean the GEOID exists in that release but points
to the wrong place. A high Valid rate confirms that when a release
matches at all, it matches to a polygon consistent with the claim's
own reported coordinates.

\textbf{Block-group boundaries.} Restricted to the released
(pluvial, \texttt{causeOfDamage == "4"}) claim population, matching
\texttt{censusBlockGroupFips} against the official 2010 decennial
block-group release yields a 93.3--100\% match rate for every loss
year from 1978 through 2015, remaining the better-matching release
through 2019 even as its raw match rate declines to 84.3--87.5\% over
2016--2019. This indicates FEMA's geocoding assigns a recent-release
boundary to each record at processing time rather than using the
historical loss-year boundary. In absolute terms the transition to the
newer (2020) release is not sharp. The raw match rate against 2020
climbs gradually with loss year rather than jumping at a single point,
reaching only 83.2\% in 2020 itself before climbing to 100\% by 2026.
Ranked against each other, however, the 2010 release is the strictly
better-matching release for every loss year from 1978 through 2019,
and the 2020 release becomes the strictly better-matching release for
every loss year from 2020 through 2026, with no exceptions across this
population (Table~\ref{tab:release-match-rate-bg}).

This clean crossover is evidence supporting a strong working
hypothesis, namely that FEMA's geocoding service itself assigns the
2010 release to claims with loss year before 2020 and the 2020 release
to claims with loss year 2020 or later, even though general
match-quality variation keeps the raw match-rate curve gradual rather
than a step. This working hypothesis is independently supported by
FEMA's own data dictionary, which describes how \texttt{censusTract} are assigned to each claim: 
\emph{``U.S. Census Bureau defined census tracts; statistical subdivisions of a county or equivalent entity that are updated prior to each decennial
census. The NFIP relies on our geocoding service to assign 11-digit
census tract codes.''} 
%
Since FEMA states outright that its own geocoding service, not the claimant, assigns
tract codes, and tract and block-group codes are two views of the same
lookup, a single geocoding service assigning a recent-release boundary
at processing time is the most direct reading of why block-group match
rates follow loss year the way they do.

This is exactly the two-release cutover \texttt{default} implements
for block group, which is why \texttt{default} uses a single cutover
year (2020) rather than a historical loss-year rule.

\textbf{ZCTA (Zip Code Tabulation Area) boundaries.} ZCTAs exist officially only from the 2000
census onward. Unlike block group, whose \texttt{default} strategy uses a
single 2010/2020 cutover, ZCTA has three configured releases (2000,
2010, 2020) and no fixed cutover year at all. Every claim's loss year,
including years well after 2000, is matched under \texttt{default} to
whichever of the three is numerically closest, so a claim with loss
year 2015 is tested against the 2010 release and a claim with loss
year 2022 against the 2020 release, continuously rather than at a
single switchover point. Most of this population's claims carry a
well-formed five-digit \texttt{reportedZipCode} and are eligible to be
tested against ZCTA boundaries.

Within this eligible set, match rates are high and far more stable
across releases than for block group, ranging 95.6--99.5\% for the
2000 release and 98.1--100\% for the 2010 and 2020 releases across
every loss year (Table~\ref{tab:release-match-rate-zcta}).
\texttt{default}, equivalent to \texttt{closest} over the configured
releases \{2000, 2010, 2020\}, matches 99.20\% of these claims. Testing
all three available ZCTA releases per claim and keeping the best match
recovers 4,749 additional matches (0.41\%) over \texttt{default} alone,
a small gap compared to the double-digit percentage-point differences
between releases seen in the block-group case above.

This stability is consistent with how \texttt{reportedZipCode} is
sourced. Unlike \texttt{censusBlockGroupFips} and \texttt{censusTract},
\texttt{reportedZipCode} is not assigned by FEMA's geocoding service.
FEMA's own data dictionary describes it as raw data ``as reported by
WYO partners,'' recorded once at claim intake rather than reassigned by
a lookup that could shift with whichever boundary release happens to
be current at processing time. With no processing-time geocoding step
to introduce a release-dependent pattern, there is no equivalent
mechanism to produce the block-group-style crossover, consistent with
the near-flat match rates observed across all three ZCTA releases.
Furthermore, the \texttt{closest} strategy aligns with existing work
that joins NFIP claims to external sources (e.g.\ the American
Community Survey)~\cite{cano_pecharroman_exposing_2024,
crespo_flood_2019} and thus we elect this strategy as the default for ZCTA.

However, as with \texttt{block\_group\_strategy}, the \texttt{zcta\_strategy} parameter remains configurable.

\subsection*{Pluvial date correction}

\textbf{Date-correction outcomes.} Table~\ref{tab:pluvial-correction-status}
gives the full \texttt{pluvialCorrectionStatus} breakdown across the
released file's 1,149,288 claims, under the default 7.62 mm constant
precipitation threshold. \texttt{no\_aorc\_data\_in\_window} arises,
for example, when a claim sits on a small land mass whose four
surrounding AORC grid points for bilinear interpolation are all ocean
pixels with no recorded precipitation.

\textbf{Pluvial precipitation threshold.}
Figure~\ref{fig:precip-histogram} and
Table~\ref{tab:precip-histogram} show the distribution of
\texttt{reportedDateMaxPrecipMm}, the maximum hourly precipitation at
each pluvial claim's triangulated location on the reported
\texttt{dateOfLoss}, before any correction is applied. This value is
populated only when AORC has valid data on that specific date, a
narrower condition than the one \texttt{pluvialCorrectionStatus} is
decided under, which instead uses the best precipitation found
anywhere across the full $\pm$7-day search window. A claim can
therefore still be \texttt{corrected} or
\texttt{no\_qualifying\_precip\_in\_window} even when AORC is missing
data on the reported date itself, so long as some other day in the
window has data, leaving \texttt{reportedDateMaxPrecipMm} undefined
for 111,866 of the released file's 1,149,288 claims. Of these, 12,425
are \texttt{before\_aorc\_coverage} (never evaluated) and 12,201 are
\texttt{no\_aorc\_data\_in\_window} (no day in the window has data, the
reported date included), while the remaining 87,240 are
\texttt{corrected} or \texttt{no\_qualifying\_precip\_in\_window}
claims resolved from a different day in the window than the one
missing data. Of the 1,037,422 claims with a defined
\texttt{reportedDateMaxPrecipMm}, 275,139 (26.5\%) fall at or below
the 7.62 mm default threshold, the population eligible to have their
date corrected under the default constant threshold.

Under the default uniform 7.62 mm threshold, 210,488 of 1,149,288 claims (18.3\%) have a
\texttt{correctedDateOfLoss} that differs from the originally reported
\texttt{dateOfLoss}. Figure~\ref{fig:threshold-sweep} and
Table~\ref{tab:threshold-sweep} show how the full
\texttt{pluvialCorrectionStatus} breakdown responds to the constant
precipitation threshold, swept over six values (2.5, 5, 7.62, 10, 15,
and 20 mm) with the search window otherwise unchanged. The
\texttt{corrected} share is not monotonic in the threshold. It rises
from 14.3\% at 2.5 mm to a peak of 19.4\% at 10 mm, then falls to
17.8\% at 20 mm, reflecting two opposing effects as the threshold
rises. The \texttt{accepted\_as\_reported} share falls monotonically
(81.0\% to 36.6\%, since fewer reported dates clear a higher bar on
their own), while the \texttt{no\_qualifying\_precip\_in\_window} share
rises monotonically (2.5\% to 43.4\%, since fewer search windows
contain any day clearing a higher bar). The \texttt{corrected} share
is what remains between these two trends at each threshold.
\texttt{no\_aorc\_data\_in\_window} and \texttt{before\_aorc\_coverage}
are each unaffected by the threshold and together account for a
constant 2.1\% of claims across the sweep.

Figure~\ref{fig:day-shift-histogram} and
Table~\ref{tab:day-shift-histogram} show, for the same six
thresholds, the distribution of the resulting shift in
\texttt{correctedDateOfLoss} away from the originally reported
\texttt{dateOfLoss}. The figure covers \texttt{corrected} claims only,
with each threshold's bars normalized by that threshold's own
\texttt{corrected} count. A shift of 0 days does not occur in this
population by construction, and the $\pm7$-day search window bounds
every shift to $[-7, 7]$. At every threshold tested, the shift is
concentrated in a small number of days. The share of corrected claims
shifting by no more than 2 days ranges from 49.1\% at 2.5 mm to 68.4\%
at 20 mm, and a shift of exactly $-1$ day (a qualifying day
immediately before the reported date) is the single most common
outcome at every threshold except 20 mm, where $+1$ day is marginally
more common. The table instead shares one denominator, the released
file's full claim count, across every column and every threshold, so

columns of \texttt{corrected} claims. \texttt{no\_qualifying\_precip\_in\_window}
and no-AORC-data claims are never assigned a shift and so fall outside
the table.

\section*{Usage Notes}

The full pipeline is run via \texttt{src/run\_pipeline.sh} in the code
repository, which executes the following six ordered scripts. Each
script reads its inputs from the previous step's output path, so once
those outputs exist any single step can be re-run on its own without
repeating the full pipeline.

\begin{enumerate}
  \item \texttt{download\_claims.py} --- fetches the raw FEMA claims
    extract and the FRED inflation series.
  \item \texttt{adjust\_inflation.py} --- Stage 1, inflation adjustment.
  \item \texttt{triangulate\_claims.py} --- Stage 2, spatial
    triangulation.
  \item \texttt{build\_aorc\_pixel\_day\_index.py} --- indexes the AORC
    pixel/days needed for pluvial claims.
  \item \texttt{fetch\_aorc\_daily\_max.py} --- fetches the corresponding
    AORC precipitation.
  \item \texttt{correct\_pluvial\_dates.py} --- Stage 3, pluvial date
    correction.
\end{enumerate}

\texttt{run\_pipeline.sh} restricts the run to pluvial claims
(\texttt{causeOfDamage == "4"}) by default, matching this dataset's
release, but this is a run-time flag rather than a hardcoded choice.
The methodological parameters described in Methods are all exposed as
command-line flags.

\begin{itemize}
  \item \texttt{triangulate\_claims.py --block-group-strategy} /
    \texttt{--zcta-strategy} --- the block-group/ZCTA boundary-release
    strategy (\texttt{default}, \texttt{closest}, \texttt{most\_recent},
    or \texttt{drop}).
  \item \texttt{triangulate\_claims.py --cause-of-damage} --- the
    \texttt{causeOfDamage} filter (\texttt{run\_pipeline.sh} passes
    \texttt{4} for pluvial).
  \item \texttt{correct\_pluvial\_dates.py --min-hourly-precip-mm} ---
    the constant precipitation threshold.
  \item \texttt{correct\_pluvial\_dates.py --threshold-netcdf} ---
    a spatially varying threshold from a NetCDF file, in place of a
    constant.
\end{itemize}

Census block-group and ZCTA shapefiles must be downloaded separately
and pointed to via \texttt{config.yaml}, while the FEMA, FRED, and
AORC inputs are fetched automatically.


\section*{Data Availability}

The derived dataset described in this paper is released under a CC-BY
4.0 license. The three upstream sources it is
built from are also public, namely FEMA's OpenFEMA FIMA NFIP Redacted Claims v2
(\url{https://www.fema.gov/openfema-data-page/fima-nfip-redacted-claims-v2}),
U.S. Census Bureau cartographic boundary files
(\url{https://www.census.gov/geographies/mapping-files/time-series/geo/carto-boundary-file.html}),
and NOAA's AORC v1.1 (public S3, \texttt{s3://noaa-nws-aorc-v1-1-1km},
no-sign-request). None impose redistribution restrictions beyond those
already stated.
